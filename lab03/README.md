## SLO хүснэгт

| Сценарио | SLI | Босго | Цонх / нөхцөл | Сонгосон үндэслэл |
|---|---|---|---|---|
| Performance | `/cart/add` latency p95 | p95 < 200ms | 20 VU, 1 мин | Локал cart endpoint бодитоор 1-5ms; 200ms нь хэт сул биш, тогтвортой хэрэглэгчийн хариу хадгалах бодит safety margin |
| Reliability | `/pay` HTTP 500/error rate | error rate < 8% | 20 VU, 1 мин | Server 5%-ийн үүрэг алдаа үүсгэдэг тул 8% нь гадна сүлжээний богино хэлбэлзлийг багтаана |
| Availability | Амжилттай бүх HTTP хүсэлт / нийт хүсэлт | >= 90% | 2 мин, 10с сервер зогсолт | 2 минутын цонх 120 секунд тул 10% гэвэл 12 секундын 100 хувийн уналтаар error budget үүсгэнэ |

Тайлан дээрх босгоууд `slo-test.js` доторх threshold-той яг таарч байна. `http_req_duration{name:cart}` p95 3.84ms, report p95 395.92ms, pay error rate 6.29%, checks 97.90% байсан тул PASS run бүх threshold-г давсан.

## Error budget тооцоо

Цагийн хувьд 2 минутын цонхонд availability≥90% нь 120×(1-0.90)=12 секундийн budget өгнө. Гэхдээ k6 checks нь цаг биш хүсэлтийн хувь бөгөөд chaos үед серверээс 5946 хүсэлт ирсэн, зөвхөн 4078 нь амжилттай болсон. Иймээс бодит availability 4078/5946×100=68.58%, error budget нь 5946×(1-0.90)=594.6 алдаатай хүсэлт болж тооцогддог. Энэ хоёр тоо таарахгүй байгаа учир нь секундийн budget ундаргын нягт хугацаа бус, тухайн хурдаар ирсэн бүх хариуг тэнцвэртэй тооцоход өөргарч байна.

Intentional FAIL run-д report threshold `p(95)<100` байсан. Үүний бодит p95 398.28ms тул FAIL гарсан; cart p95 3.85ms хэвээр байсан; k6 exit code нь 99. Linux/macOS дээр exit=99 хувилбарын утга CI pipeline-аас build-г зогсооно. `/cart/add` p95<50ms threshold-г өөрчлөхөд localhost endpoint 3.85ms тул боломжтой PASS хэвээр үлдэнэ.

## Дүгнэлт

Сценарио → SLO → threshold шилжилтэд хамгийн хэцүү нь таны сервист өгөх бодит босгыг чанга хязгаарлахаас нэмжгүй салгах явдал байв.
Performance SLI-г p95-р хэмжсэн нь нэг удаагийн удаашралд дургүйгээр олон хэрэглэгчийн туршлагыг илэрхийлсэн.
Reliability SLI-г pay-tagged http_req_failed-р тусгаарласнаар 5%-ийн 500 алдаа хэмжигдсэн.
Availability SLI-г 3 endpoint-ийн нийт checks-р тооцсон нь server crash үед шууд буурахыг батлав.
Chaos туршилт server 10 секунд унасан ч availability 68.58% болж SLO-г нэлээд ноцтой зөрчсөнийг харуулсан.
Reliability threshold мөн server уналтын үйлдэлд pay хүсэлт бүр failed болсон учраас 33.70%-д хүрч FAIL болов.
Хэрэв reliability ба availability-г тун тусдаа хадгалж metrics tag/scene тусгаарлахад нэг server уналтаас хоёр SLI зөрчдөж байсан ч шалтгаан нь тодорхой байна.
2 минутын цаг хугацааны 12 сек budget-ийг request success хувьтай нэгжээр шууд харьцуулж болохгүй учир зөрүү батлагдсан.
Иймэрхүү test нь CI-д threshold унаснаар build-ийг automatic stop хийхэд тохиромжтой.
Нийтдээ энэ лаборатори нь чанарын сценарио бичих, хэмжигдэхүйн тоо сонгох, chaos болон threshold-ийг нэг pipeline болгох ойлголтыг практиктаар баталсан.

## AI дүгнэлт

AI scenario бичихэд cart, report, pay endpoint-ийн 6 хэсгийг хурдан төлөвлөдөг давуу талтай байсан.
AI-ийн 200ms/8%/90% санал нь локал test-ийн бодит хариунд үндэслэгдсэн бөгөөд энэ лабораторид сайн.
AI-ийн санал хэрэгжилтийн 10 секундээс дээш unavailability цонх эсвэл SLI-ийн tag ялгалтыг заримдаа тайлбаргүй орхиж магадгүй.
Бид үүнийг tag-ээр endpoint тус бүрийг ялгаж, server crash тохиолдолд checks-г бүх endpoint-д хэмжихээр зассан.
Өөрийн бичсэн 6 хэсэгтэй формат нь өдөөлт, төлөв, хариу бодитоор холбогдсон учраас илүү нарийн болов.
Хэрэгжүүлэхэд AI threshold тоог шалгаж, локал 1мын pass/chaos тоон үр дүнгээр дахин үндэслэх шаардлагатай.
